

Лабораторна розширює систему управління магазином архівом проведених чеків і графом спільних покупок. Операційна база Shopcontrols проводить продаж, списує запаси й обліковує оплати в PostgreSQL. 

## 2. Навіщо окрема база

Поточний застосунок читає заголовок, рядки й оплати окремими запитами через представлення PostgreSQL. Для каталогу, запасів і проведення продажу важливі транзакції та обмеження цілісності. Для архіву поширена інша операція: відкрити вже проведений чек цілком. У MongoDB заголовок і два вкладені масиви читаються як один документ. Назви товарів та відділів фіксуються у знімку, тому подальші зміни в каталозі їх не змінять. Для старих чеків зберігаються назви, наявні на момент першого імпорту. 

Друга база потребує окремого розгортання та синхронізації. За малого обсягу й нечастих читань достатньо PostgreSQL. Окремий архів доцільно розглядати, якщо частота читань та результати вимірювань виправдовують додаткові витрати. Проведення продажу не залежить від стану архіву.

## 3–4. MongoDB та PostgreSQL

| Дані | MongoDB `receipts` | PostgreSQL `receipt_archive` |
| --- | --- | --- |
| Заголовок | `_id`, `number`, `soldAt`, `totalMinor` | `receipts` |
| Рядки з назвою товару, кількістю та ціною | `items[]` | `receipt_items` з FK на `receipts` |
| Спосіб і сума кожної оплати | `payments[]` | `receipt_payments` з FK на `receipts` |

Один документ відповідає трьом SQL-таблицям. Порядок вкладених елементів задає `position`. 

[`sql/schema.sql`](sql/schema.sql) визначає таблиці, ключі та індекси. [`src/mongo.mjs`](src/mongo.mjs) визначає структуру документів, перевірку полів та індекси. [`sql/export-shopcontrols.sql`](sql/export-shopcontrols.sql) читає тільки чеки зі статусом `posted` через наявні представлення Shopcontrols.

Імпорт додає знімки в SQL й переносить у MongoDB саме ті дані, які вже зафіксував SQL-архів. ID продажу робить повторний запуск ідемпотентним. Якщо між записами відбудеться збій, повторний імпорт доповнить MongoDB першою збереженою копією. Після імпорту скрипт звіряє всі завантажені чеки. Архів оновлюється командою імпорту.

## 5. Порівняння швидкодії

| Запит | SQL | MongoDB |
| --- | --- | --- |
| Отримати весь чек за номером | Один запит збирає заголовок, рядки та оплати | `findOne` повертає документ |
| Останні 50 чеків із заданим товаром | `EXISTS` по позиціях, індекси товару й дати | Фільтр `items.productId`, сортування та обмеження |
| Суми оплат за методами за місяць | `JOIN`, `SUM`, `GROUP BY` | `$match`, `$unwind`, `$group` |

- Генератор із фіксованим seed створює 10 000 і 100 000 чеків. Один і той самий набір завантажується в обидві БД. Частоти товарів різняться, а деякі чеки мають кілька оплат.
- Перед тестом створюються індекси й оновлюється статистика PostgreSQL. Для кожного запиту є 12 прогрівальних і 120 вимірюваних викликів на СУБД за замовчуванням. SQL і MongoDB почергово виконуються першими.
- Один Node.js процес використовує тривале підключення до кожної СУБД. Вимірюється час від виклику драйвера до отримання та перетворення всієї відповіді. Завантаження даних, порівняння відповідей та збір планів відбуваються поза вимірюванням.
- Параметри, порядок, обмеження і результат однакові. Скрипт переривається за будь-якої розбіжності. JSON-звіт записує кількість чеків, позицій та оплат, версії СУБД, медіану й p95. Для пояснення результату він зберігає плани PostgreSQL та MongoDB. 
- Вимірювання описує послідовне читання з прогрітими кешами на конкретному комп’ютері. Висновок робиться окремо для кожного запиту й обсягу. План, індекс і кількість прочитаних рядків або документів допомагають пояснити різницю.

Кожен прогін використовує власну тимчасову SQL-схему й колекцію MongoDB. Після прогону скрипт видаляє лише створені ним тимчасові структури. Архів демонстраційних і реальних чеків зберігається окремо.

## 6. Графова NoSQL-база Neo4j

Модель `(:ArchiveReceipt)-[:CONTAINS]->(:ArchiveProduct)` описує склад покупки. Окремі набори для демоданих та Shopcontrols дають змогу повторювати імпорт через `MERGE`.

| Файл | Дія |
| --- | --- |
| [schema.cypher](neo4j/schema.cypher) | Унікальні ключі вузлів у межах набору |
| [import.cypher](neo4j/import.cypher) | Імпорт чеків, товарів і зв’язків |
| [items-of-receipt.cypher](neo4j/items-of-receipt.cypher) | Товари одного чека |
| [count-receipts.cypher](neo4j/count-receipts.cypher) | Кількість чеків із вибраним товаром |
| [bought-together.cypher](neo4j/bought-together.cypher) | Топ товарів за кількістю спільних чеків |

У контрольному наборі товар №1 є у трьох чеках. Разом із ним товар №2 зустрічається двічі, а товари №3 і №4 — по одному разу. Команда `graph` звіряє це з відповіддю Neo4j. Рядки одного товару в різних відділах рахуються як одна поява товару в чеку.
